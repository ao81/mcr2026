# デバッグモード（debug/）

クランクなど決めた区間だけ、通常のログより細かい間隔（1〜2ms）で、プログラムの中の値まで記録するためのプログラムです。
記録したログを読んで次に変える値を決め、もう一度走らせる、という調整を繰り返すために使います。

- `basic/`：大会で走らせるプログラム（今までどおり）
- `debug/`：`basic/` と同じ走り方に、詳しいログを取る処理を足したプログラム

走り方は `basic/` と同じです。違うのは、microSD に `dbgNNNN.csv` がもう1つできることだけです。

---


通常走行（`DBG_TARGET=5`）は直前の特殊区間の出口から指定標識までを `TRCE` に、総合（`DBG_TARGET=6`）はスタートから同じ標識までを `FULL` に記録します。`DBG_AUTO_STOP=1` と対象の回数を設定すると、その標識の通過確定時に停止できます（`DBG_POST_MS=0`）。比較画面はCSV先頭の `trial`（設定番号）、`run`（走行番号）、`dip`、`route`（検出順の照合値）を使います。

実車への書き込みと、基準・候補を3走ずつ比べる操作は[区間測定の手順](../docs/section_measurement.md)を参照してください。

## 区間を選んで計測・調整する

Windowsではリポジトリのルートで `python tools/config_editor.py`（または `py -3 tools/config_editor.py`）、WSLでは `python3 tools/config_editor.py` を実行し、表示されたURLをBraveで開きます。Python 3.9以上を使用します。サーバはこのPCのループバックにだけ接続を受け付けます。

1. 「記録区間」でクランク・カーブ・レーンチェンジと何回目かを選び、「停止・保存を設定」→「保存」→「設定とスケッチを同期」を押します。サーバは `basic/` からデバッグ用スケッチを生成し、`debug/dbg_config.h` に選択内容を保存します。
2. Arduino IDEで `debug/debug.ino` を車に書き込みます。車は対象区間を抜けるとモーターを停止し、通常ログを閉じてから同じ番号の専用CSVをmicroSDへ保存します。D13が書き込みのために点灯し、消灯してから電源を切ります。
3. 「専用CSVで自動調整」でCSVを選ぶと、ログを取った時の設定と測定結果から次の値を計算します。差分を確認して保存し、書き込み直して再走します。結果が許容範囲内なら同じ値を表示します。

| 区間 | 完了の判定 | ファイル・自動調整 |
|---|---|---|
| クランク | クランク処理を抜けてトレースに復帰 | `CRK0001.csv`。計画と旋回進入時の推定速度から `CRANK_BRAKE_MARGIN_M` を調整 |
| レーンチェンジ | 車線変更処理を抜けてトレースに復帰 | `LANE0001.csv`。同じ方法で `LANE_BRAKE_MARGIN_M` を調整 |
| カーブ | 大曲がり状態または推定舵角5度以上が30 ms続き、その後トレース中に3度以下が70 ms継続 | `CURV0001.csv`。速度・推定舵角・ホイールベースから横加速度を推定し、設定上限を超えた場合に `CURVE_DRIVE_PERCENT` を下げる |

クランクと車線変更のマージン調整は計算による減速を有効にした走行が対象です。ログの「推定した速さ」はモデルが積み上げた値なので、そのままでは計画の速さと比べても誤差に気づけません。そこで次の実測で直してから比べます。

- 線を見つけた距離：クロスライン（ハーフライン）から曲がり角の線（中央線の切れ目）を見つけるまでの推定距離と、`COURSE_LIST` の距離の比（その間の速さの推定の比）
- 曲がり角の線の通過時間（`USE_NEW_CRANK_QUICK`）：走行プログラムが測り直した速さ。ブレーキの効きから考えてあり得ない値（線の見間違い）は使いません

直した速さで「計画の速さまで落ちてから曲がり始めるまでの距離（余裕）」を求め、余裕が目標（距離の5%、最低3cm）になるようにマージンを変えます。増やすときは1走行で最大0.03 m、減らすときは差の半分で最大0.01 mです。曲がり角の線で測り直せなかった走行では減らしません。外へはみ出した、計画の円弧で曲がれなかった場合は、少なくとも0.01 m増やします。線を見つけた距離の比が、線の通過時間を1 ms単位で数える誤差より大きくずれているときは、先に線の幅（`LINE_SEEN_EXTRA_M`、表を使わないときは `CROSS_LINE_WIDTH_M` / `HALF_LINE_WIDTH_M`）を差の半分だけ直します。

カーブでは、推定舵角から求めた曲率を50 msでならしてから横加速度にし（センサの段差による舵の揺れを横すべりと見間違えないため）、駆動中の90パーセンタイルを使います。上限を5%超えたら下げ、上限の85%より小さければ上げます（1走行で最大5ポイント）。変更後の効果は次の走行で比較してください。

区間設定ボタンは対象・回数・自動停止・終了後の待ち時間・記録間隔を設定します。初期450件ならクランク／車線変更は5 msで約2.25秒、カーブは10 msで約4.5秒を保持します。指定区間が収まらなければ記録間隔または件数を調整してください。停止理由を特定できない途中停止・欠損・対象パラメータの不一致では単走の調整を保留します。過去のDBG形式は引き続きPython解析ツールで読めます。

編集画面に戻ったときは、未編集ならディスクの更新を読み込みます。編集中に外部で書き換わった場合は「ディスクから再読込」で最新状態に戻せます。走行コードだけが変わった場合にも「保存」からデバッグ用スケッチを再生成できます。GitHub Pages（https://ao81.github.io/mcr2026/config/）でも「フォルダを開く」で直接書き戻せます。保存すると debug/ も basic/ に合わせて作り直します（sync.sh と同じ）。Braveでは最初に1回だけ brave://flags/#file-system-access-api を「Enabled」にして再起動してください。2回目からは前回のフォルダのボタンで開けます。

以下は `DBG_AUTO_STOP=0` の従来の記録手順です。

## 1. ファイル

| ファイル | 内容 |
|---|---|
| `debug.ino` ほか | `basic/` からコピーしたもの（`sync.sh` が作る。直接直さない） |
| `dbg_config.h` | デバッグモードの設定（どの区間を、何 ms ごとに記録するか） |
| `dbglog.ino` | 詳しいログを記録して書き出す処理 |
| `sync.sh` | `basic/` を `debug/` にコピーするスクリプト |
| `tools/analyze.py` | ログを読んで、まとめと次に試す値の候補を出す |
| `tools/sim_dbg.sh` | 同じプログラムを模擬のコースで走らせ、同じ形のログを作る（実機と比べる用） |

## 2. 準備（basic/ を直したら毎回）

`basic/` の走行プログラムや `config.h` を直したら、WSL で次を実行して `debug/` にコピーします。

```sh
cd ~/mcr2026
git pull
debug/sync.sh
```

`debug/config.h` を直接直しても、次に `sync.sh` を実行すると `basic/config.h` の内容に戻ります。
値を変えるときは `basic/config.h` を直してから `sync.sh` を実行してください。

## 3. 設定（dbg_config.h）

| 名前 | 初期値 | 内容 |
|---|---|---|
| `DBG_ENABLE` | 1 | 0 にすると詳しいログを取らない |
| `DBG_TARGET` | 1 | 1：クランク（pattern 100〜161）、2：レーンチェンジ（200〜202、300〜450、500〜502、600〜750）、3：時間指定、4：カーブ、5：通常走行、6：総合 |
| `DBG_TARGET_NO` | 1 | 何回目の区間を記録するか。1 = スタートして最初のクランク。0 なら止まるまで記録し続ける |
| `DBG_FROM_MS` / `DBG_TO_MS` | 0 / 1000 | `DBG_TARGET` 3 のとき、スタートから何 ms の間を記録するか |
| `DBG_INTERVAL_MS` | 2 | 記録する間隔 [ms] |
| `DBG_SAMPLES` | 450 | RAM に残す数（1個 24 バイト、450 個で 10.8KB） |
| `DBG_POST_MS` | 100 | 区間が終わった後も記録を続ける時間 [ms] |

残る時間は `DBG_INTERVAL_MS × DBG_SAMPLES` です。初期値では 2ms × 450 = 0.9 秒です。
クランクはクロスラインから曲がり終わるまで 0.5〜0.9 秒ほどなので、1ms ごとにすると始めの方が消えることがあります。
RAM には最後の 450 個だけが残り、古いものから上書きされます。区間の前の様子も、入る分だけ残ります。

書き込みの時に RAM が足りないというエラーが出たら、`DBG_SAMPLES` を減らしてください。

## 4. 走らせ方

1. Arduino IDE で `debug/debug.ino` を開いて書き込む
2. いつもどおり走らせる
3. 止まったら、プッシュスイッチを押してログを閉じる（通常のログと同じ）
4. マイコンボードの LED（D13）が一瞬点いて消えるまで待ってから、電源を切る（書き出しは 1 秒ほど）
5. microSD に `LOGNNNN.CSV`（通常のログ）と `DBGNNNN.CSV`（詳しいログ）ができる。番号は同じ

走っている間は microSD に書かず、RAM に貯めるだけです。そのため、詳しいログを取っても走りの判断のタイミングは変わりません。

記録は次のどれかで止まります。

- 選んだ区間が終わって `DBG_POST_MS` たった
- 区間の途中や前に、コースアウト・自動停止・プッシュスイッチで止まった（止まる直前の様子が残る）

## 5. ログの列

ファイルの先頭の `#` で始まる行は、記録した時の設定と計算の値です。

| 行 | 内容 |
|---|---|
| `#reason` | 記録を止めた理由（1 区間が終わった、2 停止した（区間が長く続き、始まりが上書きされる前に止めたときも 2）、3 時間指定の終わり、4 模擬の終わり）、区間に入った回数、区間に入った時間、出た時間 |
| `#switch` | `USE_NEW_*` スイッチ |
| `#param` | `config.h` の主な値と、その区間で計算した値（クランクまでの距離 `crank_to_m`、曲がる速さ `crank_entry_mps`、直進する距離 `plan_wait_m`、ハンドル角 `plan_angle`、区間に入った時と出た時の出力100%の速さ など） |

データの列は次のとおりです。

| 列 | 単位 | 内容 |
|---|---|---|
| `ms` | ms | スタートからの時間 |
| `pattern` | | 状態の番号 |
| `sensor` | | センサ 8 個（1 が白） |
| `steer_deg10` | 0.1 度 | ハンドル角度の指令（-416 = 左 41.6 度） |
| `motor_l` / `motor_r` | % | モータ出力（マイナスはブレーキ） |
| `servo_deg10` | 0.1 度 | サーボの本当の角度の推定（指令より遅れて動く） |
| `speed_mm_s` | mm/s | 推定した速さ |
| `dist_mm` | mm | ラインの終わり（円弧のときは曲がり角を見つけた所）からの距離 |
| `vmax_mm_s` | mm/s | 出力100%で走り続けたときの速さ（ラインの通過で直される） |
| `yaw_deg10` | 0.1 度 | クランクで曲がり始めてから車の向きが変わった角度（`USE_NEW_CRANK_QUICK`） |
| `line_pass_ms` | ms | 最後に測ったラインの通過時間 |
| `brake` | | 1：計算による減速でブレーキを始めた |
| `model_ok` | | 1：速さの推定を使っている。0 は元の表の動きに戻った |
| `unwind` | | 1：クランクでハンドルを戻し始めた |
| `measuring` | | 1：曲がり角の線の通過時間を測っている |

## 6. ログを読む

WSL で次を実行します（Python 3 だけで動きます）。

```sh
python3 debug/tools/analyze.py /mnt/d/DBG0001.CSV --html dbg0001.html
```

出るもの：

1. pattern の移り変わりの表（区間に入った時を 0 ms として、各 pattern の始めと終わりの速さ・距離・モータ出力・ハンドル）
2. クランクのまとめ（クロスラインの通過時間、測った速さ、ブレーキを始めた所、曲がり始めの速さと計画の速さ、ハンドルを戻し始めた時の向き、はみ出したかどうか、通常走行に戻った時間）
3. 次に試す値の候補（例：曲がり始めが計画より 10% 以上遅い → `CRANK_BRAKE_MARGIN_M` を 0.02 下げる。はみ出した → 速すぎたのか、速さは合っていたのかで分けて候補を出す）
4. `--html` を付けると、速さ・モータ出力・ハンドル角・pattern のグラフを HTML に書き出す（ブラウザで開く）

候補はログから決まった規則で出しているだけです。表とグラフも見て、変える値を決めてください。

## 7. 模擬と比べる

同じプログラムを模擬のコースで走らせ、実機と同じ形のログを作れます。

```sh
debug/tools/sim_dbg.sh sim.csv keep crank_l v_max=1.75
python3 debug/tools/analyze.py /mnt/d/DBG0001.CSV --sim sim.csv --html cmp.html
```

- 2つ目の引数 `keep` は `debug/config.h` をそのまま使うという意味です。`CRANK_BRAKE_MARGIN_M=0.03f` のように値を書き換えて試すこともできます（書き換えるのはコピーで、ファイルは変わりません）
- 3つ目はコース名、その後は模擬の車の本当の値です（`tools/course_sim/README.md` の 1-2）
- `--sim` を付けると、実機と模擬のまとめを並べ、20ms ごとの速さ・モータ・ハンドルを並べた表を出します

実機と模擬で速さや曲がり始めの時間が違う所は、模擬の車の値（`v_max`、`tau`、`grip_lat`、`servo_dps` など）が実機と合っていません。
模擬の値を変えて実機のログに近づけておくと、`config.h` の値を模擬で先に試せるので、実機で試す回数を減らせます。

## 8. 調整の進め方（クランクの例）

1. `dbg_config.h` を `DBG_TARGET 1`、`DBG_TARGET_NO 1` にして書き込み、走らせる
2. `analyze.py` でまとめを見る。はみ出した・遅すぎた所と、そのときの値を確かめる
3. （必要なら）模擬の車の値を実機に合わせ、模擬で値を変えて試す
4. `basic/config.h` の値を1つだけ変え、`sync.sh` を実行して書き込み、もう一度走らせる
5. ログの番号と変えた値をメモしておき、前のログと比べる

1回に変える値を1つにすると、どの値が効いたのかが分かります。
調整が終わったら、`basic/` を書き込んで大会用に戻します（`basic/config.h` にはもう値が入っています）。
